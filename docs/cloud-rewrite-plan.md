# 小红书运营系统重写蓝图

## 核心目标

重写成一套云端任务系统，主链路保持简单：

采集信息 -> 入库 -> 数据清洗 -> 运营分析 -> 热点/爆贴分析 -> 生成日报/周报 -> 企业微信推送

当前唯一建议保留的模块：

- 企业微信文件推送能力。
- 部分报告样式和运营分析规则可以参考，但不建议继续沿用现有本机脚本式流程。

## 工程原则

- 云端运行，不依赖本机开机。
- 所有步骤任务化，每个节点可重跑、可观察、可失败隔离。
- 数据先入库，再分析；不要边抓边拼报告。
- 报告是结果，不是系统核心。核心是稳定的数据采集和任务流水线。
- 第一版先跑通主链路，不做复杂权限和过度后台。

## 推荐架构

### 服务组成

- API 服务：FastAPI。
- Worker：Celery，执行采集、分析、报告生成、推送。
- 队列：Redis。
- 数据库：PostgreSQL。
- 面板：Next.js 或 FastAPI 模板页。第一版可以简单，但必须能看数据。
- 文件存储：服务器本地目录起步，后续换对象存储。
- 部署：Docker Compose 起步。

### 为什么这样拆

- FastAPI 负责账号、笔记、报告、任务状态的接口。
- Celery 负责耗时任务，避免一次日报命令跑死。
- PostgreSQL 承载 26 个账号、多天快照、任务日志和报告索引。
- Redis 只做队列，不做业务数据。
- 企业微信只作为最后的通知出口。

## 任务节点设计

### 1. 账号同步

任务名：`sync_accounts`

输入：

- 26 个账号配置。

输出：

- `accounts`
- `account_collection_states`

作用：

- 校验账号是否存在。
- 更新运营人、赛道、账号状态。
- 标记哪些账号需要采集。

### 2. 笔记发现

任务名：`discover_notes`

输入：

- 账号主页或 API 账号 ID。

输出：

- `notes`

作用：

- 找到账号最近发布的笔记。
- 新笔记只入库，不直接分析。
- 每条笔记记录来源、账号、发布时间、链接、采集状态。

### 3. 笔记详情刷新

任务名：`refresh_note_metrics`

输入：

- 昨天发布的笔记。
- 最近 7 天仍在增长的笔记。
- 手动补充链接。

输出：

- `note_snapshots`
- 更新 `notes.current_*` 字段。

作用：

- 刷新标题、正文、发布时间、点赞、收藏、评论、分享、浏览。
- 每次刷新都写快照，方便看增长曲线。

### 4. 数据清洗

任务名：`normalize_notes`

输入：

- 原始采集结果。

输出：

- 标准化后的笔记字段。

作用：

- 统一短链/长链。
- 统一互动数字格式。
- 过滤异常标题、空正文、登录页内容。
- 标记采集质量：`complete`、`partial`、`failed`。

### 5. 热点抓取

任务名：`collect_hotspots`

输入：

- 营销日历。
- 留学生关键词。
- 当前月份/考试季/申请季节点。

输出：

- `hotspot_items`

作用：

- 采集热点标题、链接、关键词、热度线索。
- 不要求第一版很智能，先让热点成为结构化数据。

### 6. 爆贴分析

任务名：`analyze_viral_notes`

输入：

- 昨天发布笔记。
- 最近 7 天笔记。
- 热点数据。

输出：

- `note_analyses`

作用：

- 计算爆贴分。
- 判断收藏型、互动型、转化型。
- 拆解标题、选题、正文结构、评论区承接。
- 生成可复用选题建议。

### 7. 日报生成

任务名：`build_daily_report`

输入：

- 指定日期。
- 账号快照。
- 笔记快照。
- 爆贴分析。
- 热点数据。

输出：

- Markdown
- HTML
- PDF
- `reports` 记录

日报固定模块：

- 今日数据总览。
- 今日爆贴数据。
- 今日爆贴内容分析。
- 当月营销热点。
- 留学生爆贴热点内容推荐。
- 今日帖子修改策略表。

### 8. 周报生成

任务名：`build_weekly_report`

输入：

- 指定周。

输出：

- Markdown
- HTML
- PDF
- `reports` 记录

周报重点：

- 账号排名。
- 运营人排名。
- 赛道表现。
- 爆贴复盘。
- 下周选题。
- 需要人工处理的问题。

### 9. 企业微信推送

任务名：`deliver_report`

输入：

- `report_id`

输出：

- `report_deliveries`

作用：

- 默认只推送 PDF。
- 需要时可手动补推 HTML。
- 记录发送时间、文件、结果、错误信息。

## 数据表第一版

必须有：

- `accounts`
- `account_snapshots`
- `account_collection_states`
- `notes`
- `note_snapshots`
- `manual_links`
- `hotspot_items`
- `note_analyses`
- `reports`
- `report_deliveries`
- `jobs`

不建议第一版做太多：

- 复杂审批流。
- CRM 客户管理。
- 多租户。
- 复杂权限矩阵。

## 采集建议

### 优先方案：第三方/商业 API

如果要稳定管理 26 个账号，这是最现实的主方案。

需要确认 API 是否能提供：

- 账号主页笔记列表。
- 笔记标题、正文、发布时间。
- 点赞、收藏、评论、分享、浏览。
- 账号粉丝、获赞收藏、笔记数。

### 兜底方案：云端 Playwright

只作为补充，不建议做唯一核心。

必须具备：

- 登录态管理。
- 限速。
- 失败截图。
- 失败重试。
- 账号级风控状态。

### 手动链接入口

继续保留，但定位是补充：

- 群里临时发来的链接。
- 竞品链接。
- 热点链接。

不要让日报依赖人工贴链接。

## 面板第一版

只做运营真正要看的页面：

- 总览：昨日发布、互动、爆贴、失败任务。
- 账号列表：26 个账号状态、运营人、粉丝变化、最近采集时间。
- 笔记列表：标题、账号、发布时间、互动、爆贴分、采集状态。
- 报告列表：日报/周报在线查看、下载、补推。
- 任务列表：每个节点成功/失败/重跑。

第一版面板可以朴素，但必须能共享给别人看。

## 调度策略

建议每天这样跑：

- 08:00：账号快照。
- 10:00：发现新笔记。
- 12:30：刷新昨天笔记互动数据。
- 13:00：生成日报并推送 PDF。
- 18:00：补刷新当天新增笔记。
- 每周固定时间：生成周报。

每个任务节点都要能手动触发。

## 第一阶段交付物

第一阶段只做最小可用云端版：

- PostgreSQL schema。
- FastAPI API。
- Celery worker。
- 企业微信推送复用。
- 账号管理表导入 26 个账号。
- 一个最小面板：账号、笔记、报告、任务。
- 日报任务链跑通。

验收标准：

- 关闭本机电脑，云端仍能生成日报。
- 面板能打开并查看账号、笔记、报告。
- 企业微信能收到 PDF。
- 任意一个任务失败时，能在任务页看到原因，并能单独重跑。

## 我的建议

先不要纠结面板漂亮程度，也不要先追求 AI 分析多复杂。第一阶段只盯三个指标：

- 数据能不能稳定进来。
- 任务失败能不能定位和重跑。
- 报告能不能准时生成并推送。

等这三个稳定后，再增强爆贴分析、热点推荐和页面体验。
